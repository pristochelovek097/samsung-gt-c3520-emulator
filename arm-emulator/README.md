# ARM9-ядро для C3520 — первый этап полной эмуляции

Реализован интерпретатор ARMv5TE (ARM9, little-endian) на чистом Java без зависимостей.

## Что уже работает

- 32-битная плоская память, загрузка `C3520XELaFleur.bootloader` по адресу `0x0`
- Сброс по вектору `0x0`: `b 0x600` — интерпретатор действительно исполняет код прошивки
- Инструкции: data processing (все opcode + S + флаги), ARM/Thumb branch и BX, LDR/STR/LDRB/STRB/LDRH/STRH, LDM/STM, MUL/MLA, SWI, CP15 MCR/MRC как stub
- Условное выполнение (все 15 кодов), PC-относительные константы (literal pools)
- Минимальная модель MMIO: регистр готовности по `0x70002188` (бит 19), чтобы пройти аппаратный wait-loop в `0x1bdc`
- Трассировка первых 60 инструкций

Проверка:

```sh
./build.sh
java -jar build/arm9.jar /home/bogdan/Downloads/C3520XELJ1 300
java -jar build/arm9.jar /home/bogdan/Downloads/C3520XELJ1 10000 quiet
```

## Что выяснено о прошивке

- CPU: **ARM9** (в образах строка `ER_RAM_CB_STACK_ARM9`), little-endian
- Bootloader: 41 КБ, точка входа `0x600`, сразу MMU/кэши через CP15 (`mcr p15, ...`)
- `.cla`-файлы имеют заголовок `0x2000` байт; полезная нагрузка начинается с `0x2000`, размер — первое u32 заголовка, физический адрес — u32 по смещению 8 (например `0xc0000000` для ROOT, `0xc0020000` для MAIN)
- Внутри `FS_1.image` найден манифест встроенных J2ME-сьютов (`Games_suite.jar`, `Farm_suite.jar`, ...), но сами JAR-ы в образе отсутствуют — это только список

## Второй этап (добавлено)

- Sparse-память: страницы по 4 КБ, адреса до `0xFFFFFFFF` без выделения гигабайт
- Ускоритель циклов `memset`/`memcpy` загрузчика (иначе сотни миллионов пустых итераций)
- Загрузчик зеркалится по `0x2ffe0000` — оттуда идёт BLX в `0x2ffe23dc`
- Поддержка **BLX reg**, загрузка `.cla`-payload по физическим адресам (`0xc0000000`, ...)
- **Thumb-16 интерпретатор**: почти все форматы (ALU,Branch/BL/BLX,push/pop,LDM/STM,load/store)
- Эмулятор доходит до `0x2ffe23dc → Thumb-код → 0x2fff...`, CPSR показывает Thumb + user mode
- CP15: отслеживаются `c1` (control), `c2` (TTBR), `c3` (domain); после загрузки `c1=0x5107a`
- MRS/MSR с банкированными SP/LR по режимам (USR/FIQ/IRQ/SVC/ABT/UND/SYS)
- MMU: каркас translation table walk (section/coarse page) с identity-fallback, пока MMU выключен
- Исправлены две критические ошибки Thumb: BL считался со сдвигом на 2 байта (неверные биты S/I1/I2/imm10), BLX immediate ошибочно оставлял CPU в Thumb — теперь переходит в ARM, как и в железе

Исправлено ещё одно критическое место: все Thumb-ветвления (`B<cond>`, `B`) считали цель от `PC = адрес+2`, хотя в Thumb база — `адрес+4`. Из-за этого `BEQ` в `0x2ffe605a` попадал в середину BL-пары (`0x2ffe60e8`) вместо `0x2ffe60ea`. После исправления эмулятор уходит намного глубже: проходит `0x2ffe24c8 → 0x2ffe5f64 → Thumb 0x2ffe5f6c`, возвращается к `0x0` и доходит до кода настройки MMU в `0x774..0x788`.

Также исправлен 32-битный `BLX immediate`: вторая половина пары принималась за отдельную 16-битную инструкцию и база бралась от неё, из-за чего переход попадал на 4 байта дальше. Теперь база берётся от первой половины и выравнивается по 4.

Исправлены ещё три ошибки, которые и давали `r2=0` и уход в мусор:

1. **Thumb PUSH/POP перехватывались** блоками `ADD Rd,SP,#imm` и SP-relative load/store (код `0xB5xx/0xBDxx` имеет старший полубайт `0xB`). Теперь эти паттерны исключены — `push {r4,r5,r6,lr}` и `pop {r4,r5,r6,pc}` работают, `lr` сохраняется.
2. **Знаковое расширение Thumb-ветвлений**: `imm |= 0xF000` / `0xFE00` вместо `0xFFFFF000` / `0xFFFFFE00` — ветка `B` в `0x2ffe5f08` улетала на `0x2fff5e78` вместо `0x2ffe5e78`.
3. **ARM LDM/STM (push/pop)** писали/читали не те адреса и портили writeback SP — `lr` при `pop` становится 0.

Исправлен **ARM BLX immediate**: он кодируется с `cond=1111` (NV) и должен выполняться всегда — наш `cond()` его пропускал. Теперь `blx 0x2ffe80b4` по `0x2ffe2498` корректно переводит CPU в Thumb.

После этого эмулятор проходит всю цепочку: `0x2ffe23dc → 0x2ffe24b4 → 0x2ffe5f64 → Thumb 0x2ffe5f6c → ... → 0x2ffe5f08 → 0x2ffe5e78 → ...` проходит `0x2ffe2498 → BLX в Thumb 0x2ffe80b4 → 0x2ffe8e70 → ... → 0x2ffe78a6`. Нашёл и исправил ещё одно состояние: Thumb `POP {pc}` не переключал режим по биту 0 загруженного адреса. Из-за этого возврат из `0x2ffe74a8` в ARM `0x2ffe23ec` оставался в Thumb и дальше всё разбиралось как мусор. Теперь бит 0 адреса корректно выбирает ARM/Thumb.

Исправлены **флаги CMP/CMN/TST/TEQ**: `alu(op=10)` раньше не трогал C/V и просто возвращал `a`, из-за чего `blo` в `0x2ffe8c50` крутился вечно. Теперь CMP/CMN считают перенос и переполнение.
Добавлены **LDRD/STRD** и выравнивание PC по 4 при ARM `pop {pc}` (иначе возврат шёл по нечётному адресу).

Эмулятор проходит `0x2ffe23e8 → BLX Thumb 0x2ffe7478 → 0x2ffe74a8 → ARM 0x2ffe23ec → 0x2ffe2498 → BLX Thumb 0x2ffe80b4 → 0x2ffe8e70 → ... → ARM 0x2ffe8c3c → 0x2ffe8c54 → 0x2ffe8eb8`.

Оказалось, `lr` в момент `push` по `0x2ffe8c0c` равен `0x2ffe8e95` — нечётный, то есть возврат в Thumb. ARMv5 `LDM/pop {pc}` переключает состояние по биту 0; после исправления эмулятор возвращается в Thumb `0x2ffe8e94` и исполняет настоящий код: `movs r0,#2; str r0,[r4,#4]; movs r0,#1; str r0,[r4]; ldr r0,[pc,#0x14]; str r0,[r4,#0xc]`, а затем доходит до `0x2ffe8ea0`, где стоит `b .`.

Это уже не мусор, а осознанный wait-loop прошивки после записи регистров устройства.

Добавлена модель прерываний: эмулятор распознаёт `b .` (ARM `0xEAFFFFFE` и Thumb `B` в себя), переключается в IRQ-режим, ставит I-бит, пишет `lr_irq` и берёт адрес обработчика из вектора `0x24` (= `0x2ffe08e0`). Банкированные стеки для FIQ/IRQ/SVC заданы.

После IRQ CPU заходит в настоящий обработчик `0x2ffe08e0` (`sub lr,lr,#4; push; bl 0x2ffe6f28`) и уходит в код по адресам `0x3002....`, то есть в образ ОС. Добавлен **SPSR**: при IRQ сохраняется CPSR, а `ldm sp!,{...pc}^` восстанавливает его. Эмулятор доходит до `0x2ffe6f3c` — `blx r0`, где `r0=0x3001d000`. Это точка входа ОС, но по этому адресу у нас пусто (нули), поэтому PC просто гуляет по `0x3002....`.

Начато расследование образа ОС. В полном дампе `.smd` по смещению `0x6A0EC` найдена таблица указателей на код ОС: `0x30010710, 0x300105f8, 0x3001046c, 0x30011ea4, 0x300100f0, ...` — это почти наверняка таблица, которую код читает как `[0x3001d000 + index*8]`. В `.smd` по `0x65900` лежит начало payload `ROOT`, а по `0x68510` — ещё одна таблица с `0x30010028/0x30010bd4`.

Восстановлено отображение: дескриптор по `.smd+0x66CC8` даёт `size=0xFA68, base=0x30010000`, данные начинаются с `.smd+0x66CD8` (там валидный Thumb-код). Таблица переходов лежит по `.smd+0x6A0EC` и должна быть по `0x3001d000`.

Добавлен `--load <file> <off> <len> <virt>` с **отложенной загрузкой**: загрузчик обнуляет диапазон `0x3001a098..0x3001dbb4`, поэтому образы применяются в момент `PC=0x660` (после цикла обнуления). Без этого таблица по `0x3001d000` затиралась нулями.

Также исправлено: `LDR` с регистровым офсетом (`bits==3`), повторяемость IRQ, запрет повторного входа в IRQ из IRQ-режима (иначе SP утекал на 0x38 за прерывание).

После всех фиксов `blx r0` по `0x2ffe6f3c` получает `r0=0x30010710` и **реально уходит в код ОС**: `lr=0x3001083f`. Эмулятор исполняет ~13 300 инструкций кода прошивки и останавливается с честной причиной:

```
halted: true unmapped Thumb memory at 3025e0be
```

То есть код ОС уходит за пределы загруженного куска (всего `0xFA68` байт по `0x30010000`). Добавлен автостоп при 500 подряд нулевых инструкциях — вместо бесконечного блуждания по незаполненной памяти эмулятор сразу говорит, где именно закончился образ.

Уточнение соответствия: `.smd+0x66000 → virtual 0x30010000` даёт валидный код по `0x30010710` (это `.smd+0x66710`) и по другим адресам из goto-таблицы. Эмулятор исполняет код ОС до `0x3001080c`, где стоит `bls 0x3003dcd8` — легальная ветка (C=0), уводящая в **другой регион ОС**, которого у нас нет. Простая линейная проекция `.smd` в `0x3003dcd8` даёт мусор, то есть этот регион хранится в другом месте/сжатом виде.

Карта payload'ов в `.smd` (найдена по сигнатурам):
```
bootloader        0x800
ROOT   payload    0x65900
MAIN   payload    0x86900
PAGE1  payload    0xc20900
DSP    payload    0xbbd900
RAM    payload    0x10a3900
FS_1..FS_4        0x10e3800 .. 0x3c96800
```

Текущая граница: нужно найти flash-источник для `0x3003dcd8` (или реализовать декомпрессор NAND-драйвера), иначе код ОС обрывается на первой же дальней ветке.

Разобрана таблица переводов: источник по `0x2ffe0794` — пары (счётчик, дескриптор): `0x700 × 0x0C1A0000` и `0x900 × 0x0C120000`, то есть 4096 identity-section дескрипторов с флагами AP/domain. TTBR=`0x40000000`.

## Что осталось до «полной эмуляции»

1. Настоящий CP15/MMU: TTBR пишется в `0x7b4` (`0x40000000`), domain=`0xffffffff`, MMU включается в `0x7c8`; таблица строится циклом в `0x754..0x790` из источника `0x2ffe0794` — надо реализовать translation table walk
2. Загрузка payload `.cla` по физическим адресам (`0xc0000000`, ...) и отображение их в адресное пространство CPU
3. Модель периферии: NAND, DMA, UART, GPIO, таймеры, прерывания (IRQ/FIQ)
4. Thumb-режим (BX с битом 0), расширенные ARM-инструкции (LDRD/STRD, PLD, semaphore)
5. LCD-контроллер и клавиатура, чтобы получить картинку с прошивки
6. J2ME-слой сверху — уже есть OwnJ2ME, можно подключить вместо нативной ОС

Это не один вечер: реальная загрузка ОС телефона потребует моделирования всех перечисленных блоков. Но ядро уже исполняет настоящий код загрузчика — фундамент есть.
