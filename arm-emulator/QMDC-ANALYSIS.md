### Чанк 0xA18000 (самый «простой»)
```
D (88 байт): 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
             00 00 00 00 00 00 09 ed 00 33 de 00 00 00 00 00 00
             17 3f ff ff ff ff ff ff ff ff ff ff bf ff ff ff ff
             ff ff ff fb ff ff ff ff ff ff ff ...
C (140 байт): ef ff ff ff 7f ff ff bf ff ff ff ff ff ff ff ff
             fd ff ff ff ff ff ff ff ff ff ff ff ff ff ff e0
             00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 ...
```
D почти весь нули и 0xFF, C — длинные пробеги 0xFF / 0x00: похоже на **битовый поток флагов** (0xFF = 8 бит, 0x00 = 8 бит).

## Статистика битов C (MSB-first)
| chunk | ones | zeros | Dlen | rawlen | raw/zeros | D/ones |
|---|---|---|---|---|---|---|
| 0x2000 | 894 | 1474 | 812 | 2960 | 2.01 | 0.91 |
| 0x3000 | 1010 | 1582 | 920 | 2820 | 1.78 | 0.91 |
| 0x4000 | 1153 | 1599 | 896 | 2828 | 1.77 | 0.78 |
| 0x92A000 | 358 | 474 | 120 | 3844 | 8.11 | 0.34 |
| 0xA18000 | 592 | 528 | 88 | 3832 | 7.26 | 0.15 |

`raw/zeros` не константа (2 у плотно сжатых чанков, 7–8 у почти несжатых) — значит бит флага задаёт **run-length литералов**, а не один байт.

`sum(C)` не равен `rawlen` — значит C не массив длин в байтах.

## Проверка RLE-гипотезы на чанке 0xA18000 (по просьбе)
```
D: 0xFF = 48, 0x00 = 30  (48*255 = 12240 >> raw=3832)
C: 0xFF = 27, 0x00 = 21  (27*255 = 6885 >> raw=3832)
```
Простой RLE «0xFF = 255 литералов» **не сходится**: в D 48 FF, а нужно ~15 (15*255=3825). Зато D и C при внимательном взгляде — **битовые потоки**: `FF` = 8 единичных бит, `BF` = 10111111, `FB` = 11111011, `E0` = 11100000, `AA` = 10101010. То есть границы «серий» задаются битами внутри байтов, а не самими байтами.

## Переборный тестер
`qmdc_bruteforce.py` перебирает: поток флагов C/D, MSB/LSB, бит литерала 0/1, поток параметров C/D, ширины offset 8..13 и length 2..8, minmatch 1..3, полуслова/байты. **Ни одна простая фиксированная конфигурация не даёт точный выход B** — значит поля match кодируются переменной длиной (унарные префиксы), как и предполагалось.

## TOC CB-секций (вся таблица вокруг 0x681D0..0x68A70)
Найдены записи `ER_*` с шагом 0x40. Ключевые из них (поля читаются по смещению +0x20 от имени):
```
ER_SCRAM_NCB_CODE      phys=0xC0008D04  size=0x10000  virt=0x2FFE0000
ER_SCRAM_CB_DATA_RW    phys=0xC00095BC  size=0x38000  virt=0x30000000
ER_SCRAM_CB_DATA_ZI    phys=0xC00095BC  size=0x30000  virt=0x30038000
...
```
(остальные записи TCM/RAM/NCB описывают отображения TCM и RAM, не код прошивальщика).

Арифметика `0xC0008D04 + 0x13262 = 0xC001BF66` попадает внутрь 64-КБ окна `0xC0008D04..0xC0018D04`. Но в `.smd` нет данных по этому физическому адресу: раздел ROOT из `.ptt` имеет размер 0x20000, а его распакованный `.cla` — всего 0xB5EC; остальное место в `.smd` между блоками — 0xFF-паддинг. Проверены все правдоподобные отображения (`.smd 0x66000 → 0x2FFE0000`, `.smd 0x69262`, `.smd 0x81866`) — валидной функции по `0x2FFF3262` там нет (первая инструкция `b`, не пролог).

## Область .smd 0x76740..0x84900 — результат
Вся область **сплошь 0xFF** (заполнение), никаких дескрипторов/сегментов там нет. Сразу за ней по `0x84900` начинается MAIN (QMDC-чанки). Единственный дескриптор OEM-сегмента — `0x66CC8` (`size=0xFA68, flags=0x7D800000, base=0x30010000`), его данные заканчиваются как раз на `0x76740`.

TOC CB-секций найден по `0x68630`: `ER_NCB_CODE` → `phys=0xC0008D04, size=0x10000, virt=0x2FFE0000`; `ER_SCRAM_CB_DATA_RW` → `phys=0xC00095BC, size=0x42F, virt=0x30000000`. Адрес `0x2FFF3263` не попадает ни в один загруженный сегмент (после 0x2FFEFA68 идёт 0xFF-паддинг).

## Патенты Samsung / Quram
Скачаны `TWI357224B`, `TWI393353B`, `CN101383616B` (236/339/328 КБ). Абзацы описывают generic block-matching compression (`range block`/`domain block`, distance/difference info), но **детального формата QMDC (два битовых потока, заголовок) в тексте нет** — это патенты на общий метод, а не на QMDC-container.

## Flash Loader (скачан с Google Drive)
Распакованы `Flash Loader 7.5.3 V0.6 Lite` и `7.4.7 SSG Lite` (unrar — 7z не справился с методом):
`bfldb.dll` 2.5 МБ, `bfloader.exe` 6.8 МБ, `bfloader.map` 2.2 МБ.

**`QMDC` и `Quram` в них не найдены.** В `bfloader.map` только generic compression из OpenSSL (`zlib compression`, `run-length compression`, `_decomp`, `ASN1_unpack`) — кодека Samsung QMDC в PC-утилите нет. Это подтверждает: распаковка QMDC делает **аппаратный блок в PNX4910 по адресу `0x7D000000`**, а PC-прошивальщик лишь шлёт чанки.

## Анализ `0x300130A6` (работа с `0x7D000000`)
Функция читает базу из пула (`ldr r4,[pc,#0x80]`), затем:
```
r5 = 0xFB << 0x17 = 0x7D800000   // база аппаратного блока
r7 = 1
ldr r6,[r4,r2]                   // чтение слова из структуры
cmp r1,#0; beq ...
str r7,[r5,#0x10]                // запись флага/команды в HW-регистр +0x10
ldr r3,[r5,#0x14]
lsls r3,r3,#0x1d; lsrs r3,r3,#0x1d   // выделение 1 бита готовности
cmp r3,#1; bne loop              // wait-loop готовности
```
То есть `0x7D000000+0x10` — регистр управления/запуска, `+0x14` — регистр статуса (бит 0 = готово). Прямых BL на `0x300130A6` в загруженном куске нет — вызывается через таблицу указателей.

## Полный скан .bootloader на битовую арифметику
Отсканирован весь файл (0xA174, 10333 инструкций). Плотные окна `lsl/lsr/and/eor` только в одном месте: `0x2FFE634C` — это побайтовый XOR/CRC-32 (сравнение 3 байт, `eor r4/r5`, цикл по битам), **не QMDC**. Значит декомпрессора в `.bootloader` нет. `0x2FFF3263` лежит за пределами файла (0xA174) — код оттуда должен быть в другом несжатом регионе.

## MAIN[0x0000..0x2000] — что там на самом деле
```
0000: 00 90 ad 00 00 00 00 00 00 00 02 c0 01 00 00 00
0010: 00 10 00 00 00 00 00 00 5c ff 19 01 00 00 00 00
0020: 02 00 00 00 00 00 00 00 4d 41 49 4e 00 00 00 00
```
Поля: load=0x00AD9000, phys=0xC0020000, size=0x0119FF5C, name="MAIN". Далее нули; по `0xC0..0x100` — 64 байта случайных чисел (хэш/подпись). Всего ненулевых 144 байта из 0x2000. **Таблицы индексации чанков здесь нет** — 0x2000 это просто стандартный заголовок раздела + подпись.

## Дерево вызовов (дизассембл по Capstone)
- `0x30012FA0` → сохранение CPSR/SPSR/LR, `b 0x30013514`.
- `0x30013514` — таблица переходов (`ldr pc,[pc,#-4]`), Однако адреса в таблице — `0xC010EDE5`, `0xC0A8E868`, `0xC002C798`, `0xC022866D`, `0xC0038071`, `0xC0355A81` (flash-отображение `0xC0xxxxxx`), то есть реальные обработчики лежат во flash-страницах, а не в загруженном куске `0x30010000`.
- `0x30013580` — конфигурация векторов: пишет в `[r0+#0x30]` при `r0=0`, то есть в таблицу векторов по адресу 0.
- `0x2FFE8F59` (Thumb) → `blx 0x2FFF3263` — вне загруженных областей.
- `0x2FFE80B0` → `blx 0x2FFE8F58`, `bl 0x2FFE8174`.
- `0x300130A6` — polling регистра по базе `0x7D000000`: `ldr r6,[r4,r2]`, `str r7,[r5,#0x10]`, цикл `lsls/lsrs` с однобитным тестом — это аппаратный контроллер (NAND/DMA), wait-loop готовности.

## Несжатые разделы
`IMAGE` (.bmp, 0x5000) и `LCDACT` (0x60F4) в .ptt помечены `partition_compressed=0`, но по дизассемблу это **данные** (нули/растровые данные), не код. Другого несжатого куска с декомпрессором в архиве нет.

## Скользящее окно между чанками
В `literals` предыдущего чанка `0xAD8000` (длина 0x808) **нет** целых `Conversion`/`version`/`Assertion`, но есть ровно одно `ve` по смещению `0x782`. Это подтверждает гипотезу: первые 2 байта `rsion failed` в чанке `0xAD9000` — LZ-совпадение длиной 2, ссылающееся назад в предыдущий чанк (`dist ~0x800+` в выходном буфере, то есть 11–12 бит).

## Чанк №0 — первые токены
```
D stream first 16: 30 03 00 00 f7 e6 f3 5c 5d 6e fb 6b 5d f9 7d ab
C stream first 16: 97 07 0f 7d b0 ae 9c a2 4a 11 d5 55 a4 18 22 09
literals[0:64]: 0e b5 6a 46 03 c2 0c f0 b0 eb 69 46 02 90 01 20
                ab df 03 b0 08 bc 18 47 08 b5 f6 e7 18 b5 07 c4
                69 46 f3 e7 e4 e7 1c b5 6a 46 03 c2 00 20 d3 e7
```
Первые `0x30` байт дизассемблируются в валидный Thumb без разрывов (`push {r1,r2,r3,lr}; mov r2,sp; stm; blx; ...; bx r3`), с легальными обратными ветвлениями. С `0x30` начинаются ARM-слова (`0xE59F100C` = `ldr r1,[pc,#0xc]`) — это interworking, а не разрыв. То есть первое LZ-совпадение чанка №0 лежит позже первых 48 байт.

## ВАЖНОЕ ИСПРАВЛЕНИЕ: разметка потоков сдвинута на 4 байта
Поле D = длина **D-потока вместе с 4-байтовым словом длины**. Правильная разметка:
```
D stream = data[0 : 4+D]     (слово длины + D байт)
C stream = data[4+D : 4+D+C]
literals = data[4+D+C : 4+A]
```
Подтверждение: у чанка №0 `literals` теперь начинается с валидного Thumb `0e b5 6a 46 03 c2...` (а не с мусорных `19 ff ff ff`); у последнего чанка `literals` начинается сразу с `"rsion failed\0%s: facet..."`. `qmdc_tool.py` обновлён.

Первые байты потоков после исправления (последний чанк):
```
D stream: d4 02 00 00 | 0a d6 5a 9f b5 f7 6f 22 57 a7 6c fd d6 ae 6f ...
C stream: 19 c1 f9 ce ec 4b 1c 5f b1 c1 0f 82 20 16 0f ba 2d 26 47 27 ...
literals: 72 73 69 6f 6e 20 66 61 69 6c 65 64 00 ("rsion failed\0")
```
Первый разрыв — в начале `literals`: перед `rsion` вырезано `Asse` (или `ve`). Это самый ранний токен, накопленного сдвига ещё нет.

## Последний чанк MAIN (0xAD9000) — проверка по просьбе
```
A=0xFE4 B=0x1660 C=0x114 D=0x2D4 raw=0xBFC LZ-out=0xA64
```
**raw — читаемый ASCII-код прошивки**, что подтверждает: `raw` действительно литералы:
```
04 04 a0 27 72 73 69 6f 6e 20 66 61 69 6c 65 64 00 25 73 3a 20 66 61 63 65 74
... "rsion failed\0%s: face %u not found in \"%s\" locate constraint locate excep..."
```
D (0x2D4) и C (0x114) полностью выведены в лог сессии; D начинается с `0a d6 5a 9f b5 f7...`, C — с `1a c1 91 2d 19 c1 f9 ce...`.

## Проверка унарных кодов (количество нулевых битов)
| chunk | B | raw | zeros(D) | zeros(C) | zeros(D)+zeros(C) |
|---|---|---|---|---|---|
| chunk0 | 4672 | 2960 | **2950** | 1042 | 3992 |
| 0xA18000 | 4432 | 3832 | 131 | 501 | 632 |

`zeros(D)=2950` для chunk0 почти точно равно `raw=2960` (разница 10) — сильный сигнал, что нулевой бит D завершает один унарный токен/литерал. Но для почти несжатого чанка `0xA18000` этого нет (131 против 3832): там длины кодируются run-length, один бит покрывает много байт.

при обработке потоков в обратном порядке (C, затем данные D) для chunk0 `zeros=2961` ≈ `raw=2960` (разница 1) — тоже стоит проверить при реализации.

## Криб из последнего чанка: найденные повторы в raw

Разрывы слов: `rsion failed` (нет `Asse`/`ve`), `facet` (нет пробела), `localeto constru...ct locale xceptinexpecexceptn` (нет `\0`, `exception`, `in`).

Побайтовый поиск пар (19,7), (13,5), (61,5) в D/C не дал совпадений. Битовый поиск (offset 5 бит, length 3 бита) даёт 246 попаданий в D и 68 в C — слишком много, чтобы считать формат найденным: нужны дополнительные ограничения (порядок полей, разрядность, привязка к позиции в выходе).

RAW имеет характерный паттерн **пар одинаковых байт** (`f6 f6`, `0e 0e`, `61 61`, `35 35`, `57 57`, `b9 b9`, `86 86`) — похоже на уже частично преобразованные данные (16-битные значения с повтором старшего/младшего байта), а не на чистый код. Это объясняет, почему вставка LZ-совпадений «сдвигает» адреса функций: часть повторов уже вырезана в D/C.

## 2026-11-25: новые факты по формату (патент + заголовки .cla)

### Тип сжатия в заголовке .cla
Структура заголовка (0x2000 байт, LE u32):
```
[0] размер полезной нагрузки   [2] физический адрес загрузки
[3] = 1 (флаг сжатия)           [4] = 0x1000 (размер блока)
[6] размер после декомпрессии   [8] = 2 (тип сжатия, QMDC)
```
У `ER_FLASH_CB_ROOT` все поля сжатия нулевые — ROOT не сжат и исполняется напрямую
(프로적 IRQ/MMU/flash-драйвер/таблица разделов `ER_*` по `0xC00027D0`).
DECOMPRESSOR в дампе НЕ найден: ни в `.bootloader`, ни в `.bootlcdact`, ни в ROOT
(нет битовых циклов `lsl/lsr/and/eor` + `ldrb` ни в ARM, ни в Thumb), ни в PC-утилитах
Flash Loader 7.5.3/7.4.7, ни в agent `TEXTO_pnx4908load_cs2_v00.bin`.
Итог: декомпрессор, скорее всего, в маск-РОМ SoC — его надо эмулировать独自.

### Чанки с переменным размером выхода
B — НЕ всегда 0x1000. Диапазон по MAIN: от `0xF60` до `0x25740` (153408) байт.
Для `0x858000`: `A=0xFE8 B=0x146A0 C=0x678 D=0x584 L=1000`.
То есть один 4 КБ слот распаковывается в десятки КБ (нули/повторы), а `C` при этом
всего 0x678 байт → **2 бита на 4-байтовый блок здесь физически невозможны**.
Значит `c` кодирует не каждый макроблок, а LMB/пробеги (по патенту: LMB = m MB).

### Поток `c` — 2-битные коды (проверено на плотных чанках)
Для chunk0: `C*8 = 2368`, `B/4 = 1168`, `2*(B/4) = 2336` → ровно 2 бита на MB + 32 бит.
Разбор 2-битных кодов с **LSB-first** порядком бит даёт:
```
MAIN 0x2000: коды [479,208,288,193] (00/01/10/11)
MAIN 0x3000: [494,239,301,222]
MAIN 0x10000:[537,302,358,351]   RAM 0x2000: [723,271,99,75]
```
Патентная таблица差異旗標: `00`=копия домена, `01`=global index, `10`=local index,
`11`=исключение (сырой блок). При шкале `11`→4 байт из `literals` и LSB-first получаем
`output[0:4] = 0e b5 6a 46` = валидный Thumb `push {r1,r2,r3,lr}`, затем литералы
на позициях 16, 32, 48 (в Experiments/скрипте `decode_probe`). Но `litUsed` не совпадает
с `L` (696 против 2956) — значит либо длина исключения >4 байт (LMB), либо часть
литералов относится к таблицам.

### Полярность distance flag из патента
TWI393353B FIG.13 явно: `distance flag = 0` → **новое** расстояние (считывается значение),
`distance flag = 1` → то же расстояние, что в предыдущем блоке. Ранее в экспериментах
полярность была инвертирована. Кодирование нового расстояния: 10 бит если `diff<256`,
иначе 18 бит (1 бит same + 1 бит big + 8/16 бит значения — предположение).
Проверка на 50 чанках: ни одна комбинация (полярность, 8/16, порядок бит, 0/8 бит индекса)
не даёт точного совпадения `dUsed == D*8` и `litUsed == L` одновременно →
в D, вероятно, дополнительно кодируется длина LMB/исключения, либо индексы таблиц
имеют другую разрядность.

### Поиск внешнего декодера
Sourcegrep/GitHub/Bing/DDG/Yandex: публичных реализаций QMDC нет (все совпадения —
неотносимые). `0x43444D51` и `QMDC` отсутствуют во всех бинарниках Flash Loader

### РЕШЕНО: родной декодер и Global Table найдены (2026-11-25)
- Декодер: `.bootloader 0x2FFE4190..0x2FFE4788`. Вход: `r0 = chunk+8`, `r1 = output`,
  поля `B(chunk+8) C(chunk+12) D(chunk+16)`, данные начинаются с `chunk+0x14`.

  векторной таблицей `0x2FFE9CB4`; 8 ссылок из декодера (0x4368...0x4650).
- Разметка: `C = payload[0:C]` (биты, MSB-first), `D = payload[C:C+D]` (флаги/индексы),

- Группа = 16 байт (m=4 MB = 8 short block). Бит C=0 → LMB (бит 1 = повтор domain на

  обновление расстояния (бит C=1 — то же, 0+1 — байт из D, 0+0 — uint16 из literals)
  происходит перед short block 0,2,4,6; бит флагов 1 — копия domain, 0 + бит C:
  1 — uint16 из literals, 0 — байт-индекс из D, XOR с `global[idx]`.
- `qmdc_decode2.py` даёт **100% bit-for-bit совпадение** с вызовом родной функции
  через `arm.NativeTest` (чанк 0 и слот 0xB000). На слоте 0xB000 по адресу
  `0xC002C798` (выход+0x1108) получено `e92d40 70` = `push {r4,r5,r6,lr}`.
- По пути исправлены два бага интерпретатора: CMP/TST/TEQ/CMN не ставили флаги N/Z;
  LDRH/STRH/LDRSB/LDRSH (bits 27-25=000) молча игнорировались как data-processing.
- 54 слота без QMDC: у `0x861000` A=0xfe0, у `0x9F5000` A=0xff0 → `ceil((16+A)/0x1000)=1`,

  мусор), один слот имеет magic `QMDU` по `0xADA000`. Требуется отдельная классификация.

## INTC / IRQ-диспетчер (2026-11-25)
- Вектор IRQ `0x24 -> 0x2FFE08E0`; обработчик:

Также добавлено ускорение циклов memset/memcpy ROOT по `0xC00012AC/0xC00012E4`.

- `0xC0000498` проверяет `r0`, возвращённый `0xC00004A0` (region setup): при отказе

## Причина r0=5 и состояние (2026-11-25)
- Carry в ARM/Thumb SUB/CMP уже считается беззнаково через `long` (`a & 0xFFFFFFFFL`),
  знакового сравнения `a >= b` для адресов 0xCxxxxxxx нет — версия с багом C не подтвердилась.
- Точка возврата `r0=5`: `0xC00004F6` (второй проход `0xC00004DE..0xC00004FC`),
  первый дескриптор `0xC00028A8`, Its flags `0x1403`; `0xC0000F1C` возвращает 5.
  Почему именно он не проходит — требует дальнейшего разбора проверки `0xC00004E6..EA`.
- В `--start-root` .bootloader больше не грузится по физическому 0x0.
- Честный SVC-entrance реализован (SPSR, LR_svc, cpsr=0x13|I, T=0, вектор 0x8/0xFFFF0008,
  выход с восстановлением CPSR и банковских регистров). Пока не заполнена L1 — вектор
  берётся с физического 0x8, поэтому SVC уходит в загрузчик.
- В `TraceMemory` добавлен логгер UART `0x70004000..0x7000400F` (ASCII-байты).
  До прохождения region setup до UART пока не доходим.

## Точная причина r0=5 (найдена!)
Пошаговый трейс второго прохода: отказ формируется инструкцией
`0xC0000CD2: movs r5,#5` (дальше `str r0,[sp,#4]` иreturn 5).
Ветка: `0xC0000C9C cmp r0,#3` → `0xC0000C9E blo 0xC0000CD2`, где r0 — результат
хелпера `0xC0000B36`: он Возвращает 4/3/2/1/0 в зависимости от выравнивания адреса
(1MB/64KB/4KB/1KB/невыровнено). Требуется >=3 (64KB-aligned), но хелпер вернул 0 —
адрес региона не выровнен. Первый дескриптор второго прохода `0xC00028A8`
(ER_FLASH_CB_PAGE1) даёт addr `0xA07668CC` (offset 0x7668CC), что не кратно 64KB.
В `--start-root` .bootloader убран и с 0x2FFE0000, физический 0x0 зеркалит ROOT.
Carry в CMP/SUB в ARM/Thumb проверен — беззнаковый, через long.

## Ещё один критический баг Thumb: тип сдвига immed (2026-11-25)
В `stepThumb` тип LSL/LSR/ASR immed брался как `(insn>>>9)&3`, но в Thumb он
задан стоимостью opcode: `0x0000..0x07FF = LSLS`, `0x0800..0x0FFF = LSRS`,
`0x1000..0x17FF = ASRS`. Из-за этого `0x032D lsls r5,r5,#0xC` (page size 0x1000)
исполнялось как LSR → r5=0, что ломало вычисление границ регионов и ветку
`0xC0000C9C`. Исправлено: `type = insn < 0x0800 ? 0 : insn < 0x1000 ? 1 : 2`.
После исправления вектора по физическому 0x0 стали ROOT'овыми
(`e3a00000 e3800a01 ...`), но цикл дескрипторов всё ещё не завершён.

## Поиск сдвигов продолжается: баг с маской 0x1800 (2026-11-25)
При исправлении предыдущего бага условие `if (top == 0)` было заменено на
`if (top <= 1)`, из-за чего все инструкции `0x1800..0x1FFF` (ADD/SUB register/immediate)
стали ошибочно трактоваться как ASRS — `adds r1,r1,#1` по `0x1C49` не инкрементировал r1.
Правильная граница сдвигов — `insn < 0x1800`. После исправления индекс дескриптора
в `0xC0000ED0` начал честно расти 0,1,2,..., TTBR = 0xC3BC4000, MMU-таблица заполняется.
50 000 000 инструкций хватило только на первые 2–3 дескриптора из 40 (постраничное

## Аудит флагов/условий (2026-11-25)
- `cond()` проверен: 2=CS → C, 3=CC → !C, 8=HI → C && !Z, 9=LS → !C || Z,
  10=GE → N==V, 11=LT → N!=V, 12=GT → !Z && N==V, 13=LE → Z || N!=V — верно.
- `alu()` CMP/SUB/RSB/SBC/ADD/ADC/CMN считают Carry через `long` беззнаково:

  при равенстве C=1. Формула V также стандартная. Знаковых сравнений адресов нет.
- Профиль: 44% времени — wait-loop `0xC000049C`,并非 заполнение MMU.
- Текущий отказ: `r0=2` на дескрипторе №20 (`0xC0002DA8`); хелпер `0xC0000B36`
  сообщает выравнивание 4 КБ, после чего ветка `0xC0000C9C` требует 64 КБ.

## Прорыв: инициализация 40 драйверов (2026-11-26, 15:40 MSK)

### Первопричина «краша» — баг эмулятора, не прошивки
`0xC01C24C0` вызывается с `bl` из `0xC0063802`; следующий `bl 0xC01B2B4C`
лежит **сразу** за ним без единой проверки. PC действительно доходил до
`0xC0063802`, но никогда не возвращался на `0xC0063806`.

Причина: в `ARM.stepThumb()` состояние `thumbBlInsn/thumbBlAddr` (первая
половина BL/BLX Thumb-2) **никогда не сбрасывалось**. Когда венеер
`0xC02E6128: ldr pc,[pc,#-4]` передал управление на VA `0x374`, там лежала
сиротская вторая половина BLX (`0xE87E`), и эмулятор подставил устаревший
`thumbBlInsn = 0xF123` от давнего вызова `0xC01C2564`. Получился ложный
BLX в `0xC02E5664`, откуда ARM-код уходил в векторную таблицу и бесконечный
дамп через UART → «crash dumper» `0xC036B68C`.

**Исправление:** добавлен `thumbBlPending`; вторая половина BL/BLX теперь
используется только непосредственно после первой. Сиротская `0xE8xx`
трактуется как обычная `B`, сиротская `0xF8xx` — как no-op.

## Разделение ITCM/DTCM и цепочка shutdown (2026-11-26, 17:10 MSK)

### CP15 c9: правильная декодировка

##Switch 0xC037CE8C / поиск кнопки включения (2026-11-26, 17:40 MSK)

### Что на самом деле происходит
`0xC037CE8C` — не switch, а `blx` в сервис `0xC03994C0`, который через
veneer `0xC03994CC: ldr pc,[pc,#-4]` уходит в `0xC0AA4270` (ARM):
```
0xC0AA4270: ... and r2,r2,#0xF; beq 0xC0AA42AC; ... mcr p15,0,...
```
Цепочка дальше: `0xC0AA4270 → ... → 0xC037CD79` → `0xC045232C` →
`0xC0452330: bx ip` → `0xC037CE8C` → `0xC03B355C` → сервис 0x17 →
`0xC0243868` → `0xC002B528` → `0xC03E00E4` (PowerOff) → `b .`.

###碟ссекция функции 0xC037CD68..0xC037D03E
НоFlags `0xC037CD68: push {r3,r4,r5,r6,r7,lr}`; внутри — длинный
табличный dispatch с вызовами сервисных veneer'ов по адресам
`0xC03C37B0`, `0xC03C37B4`, `0xC03C37B8`, `0xC03C37BC`, `0xC03C37C0`,
`0xC03C37C4`, `0xC03C37C8`, `0xC03C37CC`, `0xC03C37D0`, `0xC03C37D4`,
`0xC03C37D8`, `0xC03C37DC`, `0xC03C37E0`, `0xC03C37E4`, `0xC03C37E8`,
`0xC03C37EC`, `0xC03C37F0`, `0xC03C37F4`, `0xC03C37F8`, `0xC03C37FC`.
Каждая ветка завершается `b 0xC037D03E`. Ветка `0xC037CE8C` (через
0xC03994C0 → 0xC0AA4270) приводит к PowerOff. Другие ветки ведут в
сервисы 0xC0382338..0xC0382698 (конфигурация peripherals).

### Проверка PMU
- `0xC03C4A98(r4)`: `r0 = [r4+0xC]`, возвращает `bit17` (`lsl #0xE; lsr #0x1F`);
  comparing base with literal at 0xC03C4A9C and 0x78000000, otherwise assert.
- вызывается из `0xC028A184: mov r0,r4; bl 0xC03C4A98; cmp r0,#0; bne ...`
  — wait-цикл по `0x7800800C` / `0x7800000C`.
- Эксперименты: константа 0 / 1 / 0x10000 / 0x20000 / 0xFFFFFFFF и
  динамический переход 0x20000 → 0 после 64 чтений:
  * бит17=0 → outflow в PowerOff;
  * бит17=1 → вечный wait-цикл `0xC028A184`;
  * переход → PowerOff после 64 чтений.
Вывода: этот бит — не «кнопка включения», а статус наличия/готовности
устройства. Решение о выключении принимается по внутренней структуре
(сравнение в `0xC02A88C0`, вызванном из `0xC03B355E`), а не по MMIO PMU.

### Итог
Нормальная ветка включения не найдена: прерывания закрыты (I=1),
LcdController commands/pixels = 0, UART молчит. 39/40 драйверов

## Аппаратный MMU Translation Fault (2026-11-27)

В arm.rs реализован путь фолта по ARM926EJ-S:
- FAR → CP15 c6, FSR → CP15 c5 (MRC c5/c6 уже работают через cp15[5]/cp15[6]);
- `l1_desc & 3 == 0` → FSR 0x5 (Section Translation Fault),
  `l2_desc & 3 == 0` → FSR 0x7 (Page Translation Fault);
- Data Abort → vbase+0x10, LR_abt = упавший PC + 8 (ARM) / +4 (Thumb);
- Prefetch Abort → vbase+0x0C, LR_abt = PC + 4 (ARM) / +2 (Thumb);
- сброс TLB при фолте; выборка инструкций идёт через `ifetch16/translate(data=false)`.

Включение через `--strict-mmu`. При включении получаем шторм абортов:
```
#1 pc=c00588b8 far=c99a0d5c fsr=07
#1 pc=c00588b8 far=c99a0d60 fsr=07
...
#3 pc=000000ac far=fffffff8 fsr=05
#3 pc=000000ac far=fffffffc fsr=05
```
Обработчик по 0xAC застревает на FAR 0xFFFFFFFx — demand paging прошивки
в текущем состоянии таблиц не сходится. Поэтому строгий режим сделан
опциональным, а в обычном прогоне сохранён прежний fallback.

Костыльный алиас 0x3D900000 удалён — прошивка сама мапит физическую
память, прогон от этого не изменился.

Итог: RE=0, 20.39 MIPS, halt 421447876 (`PC escaped ... 005a0058`),
MMIO/IRQ-таблица/[IRQOPEN] без изменений.

## Точная причина PC=0 на шаге 421447876

Трасса 421447840..421447876:
```
421447863 c044db38  pop {r4,r5,r6,r7,pc}   sp=c3bbb620 → pc=c0464235
421447864 c0464234  pop {r1..r7,pc}        sp=c3bbb634 → pc=c036beb1
421447865 c036beb0  movs r0,r7             sp=c3bbb654
421447866 c036beb2  pop {r3,r4,r5,r6,r7,pc} sp=c3bbb654 → pc=0
421447867 00000000  (данные ITCM как код)
```
`0xC036BEB2` — эпилог функции, вход которой находится по `0xC036BD14`
(`push {r3,r4,r5,r6,r7,lr}`). Вход **не выполнялся**: в PC попал сразу
адрес эпилога `0xC036BEB1`, и 6-словный фрейм по `0xC3BBB654..0xC3BBB668`
никем не был записан (все нули).

Watch показал единственную запись возвращаемого адреса:
```
pc=c0464150 addr=c3bbb650  0 → 0xC036BEB1
```
Это `push {r1..lr}` по `0xC0464150`, после чего `pop` по `0xC0464234`
передаёт управление прямо в эпилог. То есть сбой — в цепочке
control-flow (наш bail из Log_Printf), а не в записи нуля в стек.

`--start-root --strict-mmu` за 50M: 47 032 738 data abort, первый на
шаге 1944644 (`pc=c0001334`, `far=c99a0d68`, `fsr=07`), дальше обработчик
0xAC застревает на `far=0xFFFFFFFx`. ROOT не спасает от лавины.

Итог: точный сбой локализован, но честного исправления цепочки
возвратов найти не удалось: PC=0 остаётся, halt на 421447876.
Прогон --strict-mmu оставлен опциональным.

## Проверка гипотезы про порчу SP внутри 0xC036BD14 (2026-11-27)

Трассировка входа в 0xC036BD14 за весь прогон: **ни одного входа**.
Следовательно, `push {r3..r7,lr}` этой функции никогда не выполнялся,
и фрейм по 0xC3BBB654..0xC3BBB668 не создавался — не «испортился»,
а отсутствовал изначально.

За 100 шагов до 421447866 CPU уже executes данные в 0xC036BAxx:
```
421447600 pc=c036ba46 cpsr=000000ff lr=c036b647 sp=c3bbb654
...
421447750 pc=c036beac  bl 0xC0464150  → lr=c036beb1
421447752 pc=c0464150  push {r1..lr}  → [c3bbb650]=0xC036BEB1
421447864 pc=c0464234  pop ...        → pc=c036beb1
421447866 pc=c036beb2  pop {r3..pc}   → pc=0 (фрейм нулевой)
```
То есть LR=0xC036B647 (указатель в середину кодовой области) появился
раньше, что и привело к входу в середину функции 0xC036BExx без
её пролога. SP=0xC3BBB654 не перезаписывался — он унаследован.

Итог: «порчи SP внутри 0xC036BD14» нет; первопричина — более ранний
сбой control-flow (наш bail из Log_Printf / переход в данные), который
остаётся неисправленным. halt 421447876, RE=0.

## Read-Only .text и прогон 600M (2026-11-27)

В memory.rs включена защита записи в 0xC0000000..0xC11BFFFF после
загрузки образов (`text_readonly = true` на шаге 1000). Ручной restore
венеера 0xC02D2954 удалён — watch теперь даёт 0 попаданий, код реально
не перезаписывается.

Дизассембл 0xC036B624..0xC036B664: `bl 0xC0381DC0` на 0xC036B62C,
`bl 0xC0293034` на 0xC036B642 → LR = 0xC036B647. Этот вызов был в
центре внимания, но после защиты .text сбой ушёл раньше.

Новый halt: **шаг 421343749**, `PC escaped code region at e3a02000`.
Трасса: memset-подобный цикл 0xC0451014..0xC0451054 пишет по
0xC3BC8FE8..0xC3BC8FFC (в área TTBR), затем `ldm sp!,{lr}` на
0xC045104C вытаскивает `LR=0xE3A02002` (= opcode 0xE3A02000 + 2),
и `bxeq lr` уводит в мусор. То есть защита .text убрала одну порчу,
но открыла другую — перекрытие стека и страничных таблиц.

Итог 600M (halt на 421343749): RE=0, 20.07 MIPS,
PC=0xE3A02000, CPSR=0x600000DF, HOTPC c0420ce4/c0293036/etc.
MMIO за прогон — 30 адресов (только NAND 0x7D80xxxx и LCD 0x74002000/
0x740200D4). ITCM 0x00010180 — нули, [IRQOPEN]/WFI не сработали.

## Проверка счётчика каналов 0xC9B51B48 (2026-11-27)

Лог вызовов 0xC036B624: أول вызов на шаге 30703,
`lr=0xC0276325` ( BL в 0xC0276320), r5=2. Максимальный индекс r5 за
весь прогон — **6**, а не тысячи. Значит цикл разметки каналов не
выделяет тысячи каналов.

Проверка значений 0xC9B51B48:
- 0x40..0x800 → Report_Error(1,0x22,1,0) на шаге 484448 (проверка
  0xC0419D4C, индекс >= count);
- 0x900, 0xC00, 0x1000, 0x1800, 0x2000 → RE=0.

Прогон с 0x900, 500M, text_readonly: тот же halt на шаге 421343749
(`PC escaped ... e3a02000`), что и с 0xFFFF. То есть Oncology счётчик
каналов не является причиной наезда на 0xC3BC8FFC — причина в
memset-подобном цикле 0xC0451014..0xC0451054, чей адрес назначения
попадает в область TTBR/стека, и в `ldm sp!,{lr}`=0xE3A02002.

Итог: 19.66 MIPS, RE=0, halt 421343749, MMIO 30 адресов
(NAND 0x7D80xxxx + LCD), ITCM 0x10180 нули, [IRQOPEN]/WFI нет.

## Проверка гипотезы про огромный memset (2026-11-27)

Лог всех входов в 0xC0451014 (memset): размер `r1` всегда 0x14 или 4,
ни одного вызова с `r1 > 0x10000`. Гипотеза про «30–60 МБ за один
вызов» не подтвердилась.

Зато第一步 появления SP в области TTBR зафиксирован:

Далее `add r4, sp, #0xc` даёт 0xC3BC8FFC, и memset с r1=0x14 стирает

Первопричина — накапливающийся дисбаланс стека от наших bail-ов

## Найденное кольцо утечки стека (2026-11-27)

Гистограмма инструкций, уменьшающих SP (первые 5M тактов):
```
pc=c037c67c d=024 n=6377
pc=c036b624 d=020 n=3186
pc=c02762e6 d=020 n=3186
pc=c0457084 d=020 n=1592
pc=c0457088 d=020 n=1592
pc=c0722456 d=044 n=1591
```
Один виток — ровно 2792 такта, и SP на каждом витке падает на
**0xE4 = 228 байт**:
```
1  step=558617 sp=c9b64b3c
2  step=561409 sp=c9b64a58   (-0xE4)
3  step=564201 sp=c9b64974   (-0xE4)
...
```
За 421M тактов это ~150 000 витков × 228 = ~34 МБ, что точно даёт
SP=0xC6E9E1AC на 200M-м шаге и SP=0xC3BCFFFC на 421M-м.

Кольцо: Log_Printf-обёртка 0xC0722454 → форматтер 0xC046B534 →
наш bail 0xC046B560/0xC046B85C → 0xC0457084 → 0xC02762E4 →
0xC036B624 → 0xC037C67C → новый виток.

Попытки разомкнуть:
- полный эпилог 0xC046B85A (`pop {r4,r5,r6}`) → расхождение на 561682;
- та же точка + компенсация SP += 12 → расхождение на 561680.

Оба варианта ломают control-flow раньше, поэтому оставлен рабочий
вариант. 200M: RE=0, не halted, CPSR=0x200000FF, SP утекает.

## Проверка гипотезы про выравнивание PC (2026-11-27)

В arm.rs уже корректно выровнены:
- LDR Rd,[PC,#imm]: `(addr+4) & !3`;
- ADR ADD Rd,PC,#imm: `(addr+4) & !3`;
- BLX #imm: целевой адрес `... & !3` (добавлено выравнивание базы).

Попытка выровнять базу BL (0xF000/F800) сломала загрузку: HOTPC ушёл
в 0x0000032C/0xC002009C (ловушка исключений), TAB40=0/40. Это.func
было отменено — для Thumb-2 BL используется невыровненный PC+4.

После выравнивания BLX базы sprintf по-прежнему требует наших bail-ов:
без них CPU застревает в 0x0000032C/0xC002009C. SP всё ещё утекает
(0xC6E9E1AC на 200M). Гипотеза про «+2 байта в ADR/LDR» не подтвердилась.

Заодно исправлен регресс: в коммите b3ef58e случайно исчез вызов
`cpu.step()` из главного цикла (instructions=0). Восстановлено из 390b55d.

Итог 200M: RE=0, 20.08 MIPS, CPSR=0x200000FF, SP=0xC6E9E1AC,
MMIO 30 адресов (NAND+LCD), ITCM 0x10180 нули, [IRQOPEN]/WFI нет.
